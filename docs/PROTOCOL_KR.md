# SSTD 프로토콜 명세서 v2.0

## 1. 개요 (Overview)

**Server State Telemetry Daemon (SSTD)**는 TCP 기반의 커스텀 바이너리 프로토콜을 사용합니다. 고성능, 낮은 오버헤드, 보안성을 목표로 설계되었습니다.
Noise 핸드셰이크의 MSG3 처리가 끝난 클라이언트에게 서버가 주기적으로 상태 정보를 전송하는 **Push 모델 (Streaming)**을 따릅니다. `REQ_Connect`는 선택 사항입니다.

- **엔디안 (Endianness)**: Little Endian
- **전송 계층**: TCP/IP (Nginx 등을 통한 보안 연결 지원)
- **기본 포트**: 41924

프로젝트 버전은 2.0.0이고 패킷 헤더의 wire version은 `0x01`입니다. 실제 구현은
BLAKE2b-256 및 keyed-BLAKE2b 키 파생을 사용합니다. 다른 클라이언트를 구현할 때는
프로토콜 이름뿐 아니라 `src/NoiseSession.cpp`와 Python 테스트 클라이언트의 파생 과정도 맞춰야 합니다.

## 2. 보안 레이어: Noise_XX 핸드셰이크

SSTD 패킷 교환 이전에 **Noise 프로토콜** 세션이 먼저 수립됩니다.

### 2.1. 프로토콜 식별자

```
Noise_XX_25519_ChaChaPoly_BLAKE2b
```

| 항목 | 값 |
| ---- | --- |
| DH 함수 | X25519 (Curve25519) |
| 암호화 | ChaCha20-Poly1305 (IETF 방식) |
| 해시 | BLAKE2b-256 |

### 2.2. 서버 키쌍

서버는 최초 실행 시 X25519 정적 키쌍을 생성하여 32바이트 비밀키를 `/etc/sstd/sstd.key` (권한: `0600`)에 저장합니다. 대응되는 공개키(64자리 16진수)는 연결 QR 코드에 포함됩니다.

키 처리는 `src/Config.cpp`에 있습니다. QR 모드를 포함하여 상위 디렉터리가 미리
존재하고 키를 읽거나 생성할 권한이 있어야 합니다. INI 경로를 바꿔도 키 경로는 바뀌지
않습니다. `0600` 권한 설정 실패 시 현재 구현은 경고만 기록합니다.

### 2.3. 핸드셰이크 메시지 (XX 패턴)

| 단계 | 방향 | 내용 | 크기 |
| ---- | ---- | ---- | ---- |
| MSG1 | Client → Server | 클라이언트 임시 공개키 `e` | 32바이트 |
| MSG2 | Server → Client | 서버 임시 공개키 `e` + 암호화된 서버 정적 공개키 `s, es` | 80바이트 |
| MSG3 | Client → Server | 암호화된 클라이언트 정적 공개키 `s, se` | 48바이트 |

MSG3 처리 완료 후 양측은 keyed-BLAKE2b 기반 파생 과정으로 대칭 송수신 키를 유도합니다. 이후 애플리케이션 트래픽은 ChaCha20-Poly1305로 암호화됩니다. 클라이언트는 MSG2 처리 중 QR 코드에서 고정된 `pub_key`와 서버 공개키를 비교하여 서버 신원을 검증합니다.

핸드셰이크 메시지는 고정 크기이며 전송 프레임의 길이 접두사가 없습니다.
서버는 1초 타이머마다 미완료 핸드셰이크를 검사하고 경과 시간이 **10초를 넘으면** 연결을 종료합니다.

### 2.4. 전송 프레이밍

핸드셰이크 이후 모든 메시지는 다음 형식으로 프레이밍됩니다:

```
[ 4바이트: ciphertext_length (리틀 엔디안 uint32) ] + [ 암호문 ]
```

암호문(ChaCha20-Poly1305, 16바이트 Poly1305 MAC 포함)을 복호화하면 SSTD 패킷(`SecureHeader + Body`)이 됩니다.

상태 프레임의 총 크기는 `4 + 24 + 134 + 16 = 178`바이트입니다. 클라이언트별
읽기·쓰기 버퍼는 각각 8192바이트지만 수신 파서는 암호문 길이의 최솟값·최댓값을
명시적으로 검사하지 않습니다. 이 버퍼 크기는 구현 제약이며 협상된 프로토콜 한도가
아닙니다. 관련 문제는 [REVIEW.md](../REVIEW.md)에 기록합니다.

## 3. 패킷 구조 (Packet Structure)

### 3.1. 보안 헤더 (24바이트)

헤더는 `#pragma pack(1)`로 패킹되어 있습니다.

| 오프셋 | 필드명 | 타입 | 크기 | 설명 |
| ------ | ------ | ---- | ---- | ---- |
| 0 | `magic` | `uint32_t` | 4 | 매직 넘버 (`0x53535444` = "SSTD") |
| 4 | `version` | `uint8_t` | 1 | 프로토콜 버전 (현재 `0x01`) |
| 5 | `type` | `uint8_t` | 1 | 메시지 타입 (§4 참조) |
| 6 | `client_id` | `uint16_t` | 2 | 클라이언트 식별자 (서버는 0) |
| 8 | `request_id` | `uint32_t` | 4 | 요청·시퀀스 번호 (현재 중복 검사 없음) |
| 12 | `timestamp` | `uint64_t` | 8 | Unix 타임스탬프 (ms) — 재전송 공격 방지 |
| 20 | `body_len` | `uint32_t` | 4 | 바디 페이로드 길이 |

**합계: 24바이트** (`static_assert` 검증됨)

서버는 최소 헤더 크기, `magic`, timestamp를 검사하지만 `version`, 실제 body 크기와
`body_len`의 일치 여부, 요청 시퀀스 중복 여부는 검사하지 않습니다.

## 4. 메시지 타입

| 값 | 이름 | 방향 | 설명 |
| -- | ---- | ---- | ---- |
| `0x01` | `REQ_Connect` | Client → Server | 핸드셰이크 완료 후 초기 연결 요청 |
| `0x11` | `RES_SystemStat` | Server → Client | 시스템 상태 통계 브로드캐스트 |
| `0xFF` | `ERR_General` | 양방향 | 일반 에러 |

`ERR_General`은 선언되어 있지만 현재 서버에는 오류 패킷을 보내는 경로가 없습니다.
잘못된 패킷은 대체로 연결 종료로 처리하며 알 수 없는 타입은 기존 헤더 검사를 통과하면
별도 처리 없이 성공으로 반환합니다.

## 5. 메시지 흐름

### A. Noise 핸드셰이크

1. 클라이언트가 TCP 연결을 시작합니다.
2. 클라이언트가 **MSG1** (32바이트)을 전송합니다: 임시 공개키 `e`.
3. 서버가 **MSG2** (80바이트)를 전송합니다: 서버 임시 공개키 `e` + 암호화된 서버 정적 공개키.
4. 클라이언트가 QR 코드에 저장된 `pub_key`와 서버 공개키를 비교합니다. 불일치 시 연결을 종료합니다.
5. 클라이언트가 **MSG3** (48바이트)를 전송합니다: 암호화된 클라이언트 정적 공개키.
6. 서버가 MSG3을 처리하고 세션 키를 유도합니다. 클라이언트를 `Authenticated` 상태로 전환합니다.

### B. 애플리케이션 핸드셰이크

Noise 핸드셰이크 완료 후, 클라이언트가 암호화 채널 안에서 선택적으로 `REQ_Connect (0x01)` 패킷을 전송할 수 있습니다:

- `type`: `0x01`
- `body`: 서버가 검사하지 않음 (Python 테스트 클라이언트는 `AUTH_ME` 전송)
- `timestamp`: 현재 Unix ms

서버는 `magic`과 `timestamp`를 검사하고 인증 플래그를 설정합니다. MSG3에서 이미
스트리밍이 허용되므로 이 패킷은 필수가 아니며 `AUTH_ME`도 인증 정보로 사용하지 않습니다.

### C. 데이터 스트리밍 (Push)

서버 타이머가 **1초** 주기로 실행됩니다:

1. 서버가 `SystemReader`를 통해 `SystemStats`를 수집합니다.
2. `Authenticated` 상태인 각 클라이언트에 대해:
   - SSTD 패킷 생성: `type = 0x11`, `body = SystemStats (138바이트)`
   - Noise 세션으로 암호화 (ChaCha20-Poly1305)
   - 4바이트 리틀 엔디안 길이 접두사로 프레이밍
   - 클라이언트 쓰기 버퍼에 큐잉

| 오프셋 | 타입 | 필드명 | 설명 |
| ------ | ---- | ------ | ---- |
| 0 | `uint16_t` | `valid_mask` | 유효 필드 비트마스크 |
| 2 | `uint16_t` | `reserved` | 패딩 |
| 4 | `uint8_t` | `cpu_usage` | CPU 사용량 (0–100%) |
| 5 | `uint8_t` | `mem_usage` | 메모리 사용량 (0–100%) |
| 6 | `netInfo` | `net_rx_bytes` | 네트워크 수신 통계 (20바이트) |
| 26 | `netInfo` | `net_tx_bytes` | 네트워크 송신 통계 (20바이트) |
| 46 | `uint32_t` | `proc_count` | 실행 중인 프로세스 수 |
| 50 | `uint32_t` | `total_proc_count` | 전체 프로세스 수 |
| 54 | `uint16_t` | `net_user_count` | established TCP 연결의 고유 peer 수 |
| 56 | `uint16_t` | `connected_user_count` | utmp 기준 로그인 사용자 수 |
| 58 | `uint32_t` | `uptime_secs` | 시스템 가동 시간 (초) |
| 62 | `fdInfo` | `fd_info` | 파일 디스크립터 정보 (8바이트) |
| 70 | `DiskSummary` | `disk_info` | 마운트 포인트별 디스크 사용량 (64바이트) |
| 134 | `uint16_t` | `daemon_cpu_usage` | SSTD 프로세스 CPU 점유율, 0.01% 단위 |
| 136 | `uint16_t` | `daemon_mem_usage` | SSTD 상주 메모리 점유율, 0.01% 단위 |

**합계: 138바이트** (`static_assert` 검증됨)

데몬 필드는 `0..10000`을 0.00–100.00%로 해석하며, 0.01% 단위로 반올림합니다.
`65535` (`0xFFFF`)는 미측정 또는 측정 실패입니다. 시작·재시작 후 첫 CPU
샘플도 미측정입니다. 실제 0%와 구분하며, 기존 `valid_mask`는 새 필드의
유효성을 나타내지 않습니다. 기존 수집 루프에서 함께 갱신합니다.

- CPU: `100 × 프로세스 CPU 시간 증가량 / 실제 경과 시간 / 온라인 CPU 수`.
  `CLOCK_PROCESS_CPUTIME_ID`로 SSTD의 모든 스레드를 합산하며 자식 프로세스는
  제외합니다. 경과 시간은 단조 시계를 사용합니다. 4코어 서버에서 한 코어를
  완전히 사용하면 25.00% (`2500`)입니다.
- 메모리: `/proc/self/status`의 `VmRSS / /proc/meminfo`의 `MemTotal × 100`.
  두 값은 kB 단위입니다. RSS는 공유 상주 페이지를 포함하는 커널의 근사값이며,
  전용 메모리나 최대 사용량이 아닙니다.
- 분모는 데몬에서 보이는 호스트 자원입니다. 컨테이너의 cgroup 제한을 기준으로
  계산하지 않습니다. 결과는 100.00% 이하로 제한합니다.

필드는 본문 끝에 추가하며 기존 0–133바이트의 배치는 유지합니다. 헤더 버전은
`0x01`을 유지하고 `body_len`으로 기존 134바이트와 신규 138바이트를 구분합니다.
본문을 134바이트로 고정해 읽는 클라이언트는 배포 전에 수정해야 합니다.
평문은 162바이트, 암호화 전송 프레임은 `4 + 162 + 16 = 182`바이트입니다.
Python 수신 예제는 신규 138바이트 본문을 사용합니다.

근거: [프로세스 CPU 시계](https://man7.org/linux/man-pages/man2/clock_gettime.2.html),
[Linux proc 카운터](https://www.kernel.org/doc/html/latest/filesystems/proc.html).

## 7. 보안

1. **서버 신원 검증**: 클라이언트는 QR 코드의 `pub_key`로 서버 신원을 검증합니다. 현재 서버는 별도 클라이언트 신원이나 허용 목록을 검증하지 않고 MSG3 완료 시 스트리밍을 허용합니다.
2. **timestamp 검사**: 의도한 허용 범위는 과거 5초부터 미래 1초까지지만, unsigned `now_ms - pkt_ts` 뺄셈 때문에 서버가 읽은 시각보다 1ms만 앞서도 underflow로 거부됩니다. 일반적인 Unix timestamp에서 실제 허용 범위는 `[now_ms - 5000, now_ms]`입니다. timestamp 검사만으로 요청 중복을 제거하지는 않습니다.
3. **전방 비밀성 (Forward Secrecy)**: 각 세션에서 임시 X25519 키를 사용하여, 장기 키가 노출되어도 과거 세션이 보호됩니다.
4. **키 저장**: 서버 비밀키는 `/etc/sstd/sstd.key` (권한 `0600`)에 저장됩니다. 키 교체 시 파일을 삭제하고 데몬을 재시작합니다.
5. **핸드셰이크 타임아웃**: 1초 타이머 검사 시 경과 시간이 10초를 넘긴 미완료 연결을 종료합니다.

## 8. 연결 URI 스킴

클라이언트의 손쉬운 서버 접속을 위해 정형화된 URI 스킴을 제공합니다. `./sstd --show-qr` 실행 시 터미널 QR 코드로 출력됩니다.

**포맷:**

```
sst://server?name=<서버_이름>&ip=<IP_또는_호스트>&port=<포트>&pub_key=<서버_공개키>&ts=<Unix_타임스탬프>
```

**파라미터:**

| 파라미터 | 설명 |
| -------- | ---- |
| `name` | URL 인코딩된 서버 표시 이름 |
| `ip` | 외부 IP 주소 또는 호스트명 |
| `port` | 외부 포트 번호 |
| `pub_key` | 서버 X25519 정적 공개키 (64자리 소문자 16진수) |
| `ts` | QR 코드 생성 시각 (Unix 초) — 최신성 표시용 |

**예시:**

```
sst://server?name=SST-DEV-01&ip=192.168.0.10&port=9500&pub_key=0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef&ts=1748000000
```
